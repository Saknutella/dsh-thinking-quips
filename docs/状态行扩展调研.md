## 0. 结论速览

| 问题 | 可行? | 推荐做法 | 代价 |
| --- | --- | --- | --- |
| 鲸鱼素材动态自指向(不复制文件) | **可行** | 从文档里那份内联 CSS 的 CSSOM 里读 `mask` 的 data URI | ~15 行纯函数;拿不到就 fail-soft 退回自绘 |

## 1. 素材的动态引用

### 1.1 事实:素材本来就在文档里

ADPN 不是外链资源,它通过一段**内联 `<style>`** 进入页面(实测注入块):

```js
const css$13 = ".EvIC1a_frame{…}  …  .EvIC1a_runningWhaleAnimated{…mask:url(data:image/png;base64,…)…}";
const tagId$13 = "@deepseek-ai/dsh-client-ui-chat/ChatView.module.css";
if (typeof document !== "undefined" && document.querySelector("style[data-plugin-css=" + JSON.stringify(tagId$13) + "]") === null) {
  const tag = document.createElement("style");
  tag.dataset.plugin = "@deepseek-ai/dsh-client-ui-chat";
  tag.dataset.pluginCss = tagId$13;
  tag.textContent = css$13;
  document.head.appendChild(tag);
}
```

鲸鱼那条规则在这段 CSS 的第 **3,199** 个字符处,外面还套着
`@supports (mask-mode:alpha) and (mask-image:url(''))` → `@media (prefers-reduced-motion:no-preference) and (forced-colors:none)`。
所以页面上随时可以用两个选择器找到它:

```js
document.querySelector('style[data-plugin-css="@deepseek-ai/dsh-client-ui-chat/ChatView.module.css"]')
```

### 1.2 路线 A:CSSOM 扫描(推荐)

```js
/** 递归是因为规则被 @supports / @media 包着 —— 只看顶层 cssRules 会漏掉。 */
function collectWhaleMask(rules, out = []) {
  for (const rule of rules ?? []) {
    if (rule.cssRules) collectWhaleMask(rule.cssRules, out);
    if (!/runningWhaleAnimated/i.test(rule.selectorText ?? "")) continue;
    const hit = /data:image\/png;base64,[A-Za-z0-9+/=]+/.exec(rule.cssText ?? "");
    if (hit) out.push(hit[0]);
  }
  return out;
}
```

实测(用真实规则树形状喂给这个 walker):`@supports > @media > 规则` 三层嵌套与无嵌套的平铺表都能取到
**同一个、逐字相同的 28,866 字符 data URI**。

- **优点**:不需要"回合正在跑"(设置页的图标预览也能用);零字节复制;DSH 换素材时自动跟上。
- **代价/风险**:
  - 浏览器侧 `styleSheets[i].cssRules` 与嵌套规则的访问**未验证**(本机跑不了浏览器;已用重建的规则树验证了遍历与提取逻辑本身)。
  - 样式注入的**时机**要处理:插件 `apply` 可能早于 chat bundle 物化 → 要懒解析并观察 `<head>` 的新增 `<style>`,而不是只在 apply 里读一次。
  - DSH 改名/改属性/把 CSS 换成跨源资源都会让它失效 → 必须 fail-soft:取不到就退回插件自绘的图标,而不是抛错。

### 1.3 路线 B:克隆活节点

```js
const live = document.querySelector('[class*="runningWhaleAnimated"]');
const clone = live?.cloneNode(true); // 带同名 class,自动继承 DSH 的 mask/颜色/降级规则
```

- **优点**:代码最少;动画、`currentColor` 着色、`prefers-reduced-motion` 与 `forced-colors` 的降级全部继承。
- **缺点**:只在回合运行时有(`display:none` 的时候也在,但非回合根本不存在);被克隆的 span 是
  `position:absolute; inset:0`,得自己给它一个定尺寸的定位父容器;要插进**自己的**容器,别插进 DSH 的树里跟 React 抢节点。

### 1.4 不推荐的两条

- **fetch 自己的 bundle 文本再正则**:要把 ~565 KB 的 chat bundle 拉一遍,而且违反工作区"不发网络请求"的约定。
- **host 侧读 `node_modules` 再开路由**:`link:` 插件对本机恰好能解析到
  `profiles/node_modules/@deepseek-ai/...`(Node 会向上找),但这依赖 profile 的 hoist 布局,换 profile/包装方式就崩,
  还得自己接 Web server 路由 —— 复杂度远大于收益。

### 1.5 还有一条最省事的路

**不隐藏 DSH 自己的图标**就完事了:`indicatorOnly` 模式本来就允许与 DSH 的原生指示器共存。
如果"原生鲸鱼"是想要的效果之一,把它做成"跟随 DSH"这个选项,比抓到字节更稳。

## 2. 用时功能

### 2.1 格式化:纯函数,已验证与 DSH 逐字一致

DSH 的实现(从 bundle 里原样取出,8 行):秒数取整 → 时/分/秒 → 每段配一个 i18n 单位 key;
`hours>0` 时**也会**输出 0 分,所以 1 小时显示成 `1小时0分0秒`;`en` 的单位串自带尾随空格(`"h "`/`"m "`/`"s"`)。

把"候选实现"与 DSH **自己的函数**在同 13 组输入上对拍:

| ms | DSH(zh) | 候选(zh) | DSH(en) | 候选(en) |
| --- | --- | --- | --- | --- |
| 0 / 1 / 999 | `0秒` | `0秒` | `0s` | `0s` |
| 1000 / 1500 | `1秒` | `1秒` | `1s` | `1s` |
| 59000 | `59秒` | `59秒` | `59s` | `59s` |
| 60000 / 61000 | `1分0秒` / `1分1秒` | 同 | `1m 0s` / `1m 1s` | 同 |
| 149000 | `2分29秒` | 同 | `2m 29s` | 同 |
| 3600000 | `1小时0分0秒` | 同 | `1h 0m 0s` | 同 |
| 3723000 | `1小时2分3秒` | 同 | `1h 2m 3s` | 同 |
| 90061000 | `25小时1分1秒` | 同 | `25h 1m 1s` | 同 |
| -5000 | `0秒` | 同 | `0s` | 同 |

**差异 0/13**。也就是说:复刻 DSH 的口径没有难度;真正的选择只是**要不要**照抄它那个
`1小时0分0秒` 的怪癖(建议照抄,省得用户看到两套口径)。

候选实现(与上面表格逐字对应,单位表刻意保留 en 的尾随空格):

```js
const DURATION_UNITS = {
  zh: { hour: "小时", minute: "分", second: "秒" },
  en: { hour: "h ", minute: "m ", second: "s" }, // DSH 的 en 单位自带尾随空格
};

/** 与 DSH 的 formatRunDuration 同口径。 */
function formatDuration(ms, locale) {
  const unit = DURATION_UNITS[locale] ?? DURATION_UNITS.en;
  const total = Math.max(0, Math.floor(ms / 1000));
  const hours = Math.floor(total / 3600);
  const minutes = Math.floor(total / 60) % 60;
  const seconds = total % 60;
  let text = "";
  if (hours > 0) text += String(hours) + unit.hour;
  if (total >= 60) text += String(minutes) + unit.minute;
  return text + String(seconds) + unit.second;
}
```

### 2.2 startTime 从哪来(三条路线)

现有插件在 `apply()` 里有一个 `const start = Date.now()`,但那是**插件加载**时刻,用于 quip 轮播;
页面加载后可能过很久才有回合,所以**不能拿它当回合起点**。

**路线 A —— 自计时(起点 = 运行行出现)**

`[data-chat-running]` 元素由 `RunningStatus` 在回合运行时挂载,出现即近似回合开始(差一帧)。
起点随元素出现记录,元素消失即归零。
简单、零依赖;唯一不准的场景是"中途接管"(刷新页面/切回会话时回合已经跑了一会儿)。

**路线 B —— 用 DSH 自己渲染的用时校准一次**

0.2 的可见标签里**本来就有**用时(`chat.deepDivingFor` = `深度求索中，用时 {duration} ···`),
而这条标签是每秒刷新的。插件在接管那一刻解析一次,就能把起点校正为
`startTime = Date.now() - parsedMs`:

- 回合刚开始时标签还是 `深度求索中`(没有用时)→ 解析不到,那就按 A 从 0 起算(此时本来也接近 0);
- 中途接管时标签已经带用时 → 立刻校准到真实值。

解析表就是 2.1 那张单位表的反向映射(zh `小时/分/秒`、en `h /m /s`),与格式化共用一份常量。
不依赖任何内部服务,是最省事又够准的做法。

**路线 C —— 走服务拿权威时刻(可行但换复杂度)**

0.2 的公开服务确实带着回合时间,链路是(类型与运行时赋值都核对过):

```js
const binding = ctx.uiConversation.binding(sessionId);      // uiConversation 服务
const turn    = binding.openTurn.getSnapshot();             // 最新仍打开的回合号,可能 undefined
const chat    = binding.target("chat").getSnapshot();       // ChatSnapshot
const start   = chat?.legacy.turnTimings.get(turn)?.startTime; // 回合开始(ms epoch)
```

依据:`ConversationBinding` 的 `openTurn` 文档写着"latest turn number, undefined unless its start is loaded and it remains open";
`ChatSnapshot.legacy.turnTimings` 在 bundle 里由 `updateTimeline` 用 `turn.start.time` 填充(实测代码)。

**卡点在"当前会话 id"**:`ISessions`(`ctx.sessions`)只有 `ids/byId/phase/projectionsBySession`,**没有选中项**;
`UiSession.current` 是 private;公开的只有 `uiSession.sessionStatus`(每会话的 `running` 布尔)。
所以要走路线 C,得先解决"我现在看的是哪个会话":

- 要么注册一个**会话作用域**的隐形组件(scope `session` / `session-maybe` 的 props 里带 `sessionId`);
- 要么从 `sessionStatus` 里挑 `running === true` 的会话(多会话并发时不可靠)。

> **未验证**:`binding.target("chat")` 的订阅/激活副作用,以及整条链在活的浏览器客户端里的行为 —— 本次只做了静态核对。

### 2.3 渲染与既有功能的关系

- 插件在 0.2 上本来就要接管可见行(见 [05 §8](../../../docs/05-DSH-0.2-运行状态行变更.md)),再加一个 `.tq-clock` span 是顺手的事;
- 接管之后 DSH 的每秒重写就挠不到我们自己的节点了(这正是 05 里那条第 3 点要求);
- `indicatorOnly` 模式下 DSH 自己的用时仍在,插件不该重复显示 → 这个开关要有明确语义。

### 2.4 两种运行模式

纯 DOM + 无桌面桥 → webui 与 desktop 一套代码;AGENTS §6 的模式检测在这里用不到。
但若做成**新插件**,模板要求的"两模式断言"仍要补齐。

### 2.5 验证方案(离线可跑)

1. `formatDuration(ms, locale)` 的 13 组样例断言(含 `0`、负值、跨分/时/25 小时);
2. 用 0.2 形状的 DOM 固件(`[data-chat-running]` + 隐藏 `role="status"` span + `runningText`)跑真实 `lib/client.js`:
   断言 loader 注入可见容器、quip 落在可见行、时钟随 `Date.now()` 前进;
3. 回合结束 → 计时归零;新回合重新开始;
4. 标签校准:固件先给一个 `深度求索中，用时 1分5秒 ···`,断言起点被校正为 `-65000`;
5. locale 切换 zh↔en 后单位跟着变。
